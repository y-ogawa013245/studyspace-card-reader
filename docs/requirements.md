# 要件定義 (Requirements)

本書は、「StudySpace 入退室管理システム」におけるICカードリーダー端末の機能要件、非機能要件、および制約事項を定義します。

---

## 1. システム目的・概要

自習室「StudySpace」の入退室管理において、利用者のICカード（FeliCa）をかざすことで、端末が自動的にカードの識別番号（IDm）を読み取り、自作REST APIサーバーへHTTPS POSTで送信する単体稼働型端末を構築します。
PCへの常時接続は不要とし、電源供給のみで自律して稼働します。

---

## 2. 機能要件 (Functional Requirements)

| ID | 項目 | 内容 | 状態 |
| :--- | :--- | :--- | :--- |
| **FR-01** | 自動起動・初期化 | 電源投入（USB給電）時に自律起動し、Wi-Fi接続およびNFCユニットの初期化を行う。 | 定義済 |
| **FR-02** | FeliCa読み取り | NFC Universal Unitを用いてFeliCaカード（交通系ICカード：Suica, PASMO等）のIDmを取得する。 | 定義済 |
| **FR-03** | 取得データの限定 | 読み取り対象データは原則としてカード固有のIDmのみとし、カード内の個人情報や残高等の私的データにはアクセスしない。 | 定義済 |
| **FR-04** | チャタリング・連続読取防止 | 同一カードをかざし続けた場合の多重送信を防止するため、インターバル制限（クールダウン）またはカード離脱検出を行う。 | 定義済 |
| **FR-05** | API送信 | 取得したIDm、端末識別子等をJSON形式で自作REST APIへHTTPS POST送信する。 | 定義済 |
| **FR-06** | 状態通知（フィードバック） | 端末のLED（ATOMS3 Lite内蔵）を利用し、待機中、読み取り成功、通信成功、エラー等を視覚的にフィードバックする。 | 定義済 |
| **FR-07** | オフライン・再接続処理 | Wi-Fi切断時は自動で再接続を試行し、通信エラー時もハングアップせず待機状態へ復帰する。 | 定義済 |

## 3. 非機能要件 (Non-Functional Requirements)

### 3.1 信頼性・可用性
- **スタンドアロン自律稼働**: PC不要で24時間連続通電・稼働に耐えうる設計とする。
- **耐障害性**: Wi-Fi瞬断やAPIサーバー一時停止時にもWatchdog等でハングアップを回避し、自動復旧する。

### 3.2 セキュリティ
- **セキュア通信**: APIサーバーとの通信はすべてHTTPS（TLS）を用い、証明書検証（CA証明書照合）を原則有効とする（検証を無効化しない）。
- **秘匿情報の保護**: Wi-Fi SSID/パスワードやAPI認証トークンはソースコードにハードコードせず、ビルド時注入（環境変数）または保護された領域で管理する。

### 3.3 性能
- **読み取り〜送信レスポンス**: カード検知からAPI送信完了・LED通知までを数秒以内（通常1〜2秒以内を目標）で完了する。

---

## 4. 制約事項 (Constraints)

1. **ハードウェア**:
   - マイコン: M5Stack ATOMS3 Lite (ESP32-S3)
   - NFCリーダー: M5Stack NFC Universal Unit (ST25R3916 / U216)
   - インターフェース: Grove (I2C)
2. **コスト・ライセンス**:
   - 無料およびオープンソースのツール・ライブラリ（Arduinoフレームワーク、PlatformIO、M5Unit-NFC等）のみを使用し、有料サービス・ライブラリは導入しない。
3. **データプライバシー**:
   - 取得する情報はIDmのみとし、システム側でユーザーアカウントと紐付ける設計とする。

## 5. 未確定事項・要検証項目

> [!NOTE]
> 以下の項目は現時点で確定しておらず、今後の開発・実機検証フェーズで確定させる予定です。

- [ ] **API仕様詳細**: 正式なエンドポイントURL、リクエストスキーマ、認証ヘッダー仕様（`api-spec.md` 参照）。
- [ ] **設定値の注入方式**: Wi-FiやAPIトークンの設定方法（ビルド時の `include/config.h` / `credentials.h` か、初回セットアップ時のWi-Fi Manager等の採用か）。
- [ ] **オフラインキューイング要否**: ネットワーク切断時にIDmをローカル（SPIFFS/NVS）に一時保存して後送するか、即時エラーとして利用者に再タッチを促すか。
- [ ] **LEDカラー・点灯パターン設計**: 状態遷移ごとの色（待機: 青/緑、読取: 白、送信成功: 緑、失敗: 赤など）の最終決定。
