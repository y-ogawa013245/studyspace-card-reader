# API送信仕様 (API Specification)

本書は、`studyspace-card-reader` から自作REST APIサーバー（StudySpace バックエンド）に対してカード検知情報を送信する際のHTTP/REST通信仕様を定義します。

---

## 1. 概要

- **プロトコル**: HTTPS (TLS 1.2 / 1.3)
- **メソッド**: `POST`
- **データフォーマット**: `application/json; charset=utf-8`
- **セキュリティ方針**:
  - 通信経路の改ざん・盗聴を防ぐため、HTTPは不許可（常時HTTPS）。
  - ESP32のTLS証明書検証（Root CA証明書の検証）を原則として有効とし、`setInsecure()` 等による無条件スキップは行いません。

---

## 2. エンドポイント仕様 (暫定案)

> [!NOTE]
> エンドポイントパスおよびホスト名は、バックエンド開発との調整により確定します。現時点では以下の設計を前提とします。

- **URL**: `https://api.studyspace.example.com/v1/card-events` *(要確定)*
- **メソッド**: `POST`

### 2.1 リクエストヘッダー

| ヘッダー名 | 設定値 / 例 | 必須 | 説明 |
| :--- | :--- | :---: | :--- |
| `Content-Type` | `application/json` | ○ | JSONペイロード |
| `Authorization` | `Bearer <DEVICE_API_TOKEN>` | ○ | 端末認証用トークン |
| `X-Device-Id` | `reader-atom-01` | △ | 送信元リーダー端末の識別子 *(要検討)* |

### 2.2 リクエストボディ (JSON)

```json
{
  "device_id": "reader-atom-01",
  "card_idm": "012E456789ABCDEF",
  "card_type": "felica",
  "read_at": "2026-10-26T20:30:00Z"
}
```

#### フィールド説明

| フィールド名 | 型 | 必須 | 説明 |
| :--- | :---: | :---: | :--- |
| `device_id` | string | ○ | 設置端末の一意識別子（MACアドレスまたは端末設定値） |
| `card_idm` | string | ○ | 読み取ったFeliCa IDm（16進数大文字文字列 16文字） |
| `card_type` | string | △ | カード規格識別子（`felica` 固定または省略可） |
| `read_at` | string | △ | 読み取りタイムスタンプ (ISO 8601形式、NTP時刻取得時) |

## 3. レスポンス仕様

### 3.1 成功レスポンス (200 OK / 201 Created)

カード読み取り・入退室処理の受付が完了した場合。

```json
{
  "status": "success",
  "event_type": "check_in",
  "user_name": "山田 太郎",
  "message": "入室を記録しました"
}
```

### 3.2 エラーレスポンス

| HTTPステータス | 原因 | 端末側の動作 |
| :---: | :--- | :--- |
| **400 Bad Request** | リクエストJSON構文異常、パラメータ不足 | 端末LED赤点滅（2秒）。ログ出力。再送せず待機復帰。 |
| **401 / 403** | 端末認証トークン不一致、権限不正 | 端末LED赤点灯。重大エラーとして待機状態へ戻る（要トークン確認）。 |
| **404 Not Found** | 未登録のICカード（システムに紐付いていない） | 端末LED黄/橙点滅（1.5秒）。未登録カード通知。 |
| **429 Too Many Requests**| 同一カードの短時間多重送信 | スキップ（チャタリング扱い）。 |
| **500 / 502 / 503** | サーバー側内部エラー・メンテナンス | 端末LED赤点滅。リトライ上限まで待機後、待機復帰。 |

---

## 4. エラー処理・タイムアウト設計

1. **タイムアウト**:
   - 接続タイムアウト: 3秒
   - 読取/レスポンスタイムアウト: 5秒
2. **通信切断・リトライ**:
   - HTTP通信失敗時（Wi-Fi切断やDNS解決エラーを含む）は、即時再送による輻輳を防ぐため、端末側での自動再送は最大1〜2回（短インターバル）にとどめ、失敗した場合は利用者にLED（赤色）でエラーを通知して再タッチを促します。
3. **証明書管理**:
   - APIサーバーのRoot CA証明書（例: Let's Encrypt ISRG Root X1 等）をファームウェア内またはSPIFFSに組み込み、TLS検証を行います。

## 5. 未確定事項・要検証項目

- [ ] **バックエンドAPIの正式エンドポイント・URL**: ドメインおよびパス設計の合意。
- [ ] **レスポンス構造**: `event_type` (入室/退室/自動判定) や利用者名などのレスポンスフィールド仕様。
- [ ] **端末時刻 (NTP) 依存度**: リクエストに `read_at` を含めるか、サーバー側の受信時刻を基準とするか（後者であればマイコンのNTP同期不要となり起動が高速化）。
- [ ] **Root CA証明書の更新方針**: 有効期限対策（証明書バンドル方式の選定）。
